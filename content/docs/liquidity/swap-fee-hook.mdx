`StaticsSwapFeeHook` charges a configured fee on both realized swap legs of a registered public pool. This **hook fee is separate from the creator-selected native Uniswap v4 LP fee**. A user LP earns the native fee through PositionManager accounting; Statics routes the bilateral hook fee through its own reservations.

:::warning Source and deployment
These are current Phase 1 source defaults. Read the actual fee rates and allocation on the target release before quoting a trade.
:::

## Rates and allocation

The source launch default is **5 BPS input plus 5 BPS output**. Both legs together may not exceed 200 BPS. A general-pool creator can choose an initial rate at or above the live default for each leg. Selecting exactly the default inherits future default changes; selecting a higher leg stores a PoolId override. Governance can change the default, replace a PoolId override, or clear one back to inheritance. The creator has no post-creation fee setter.

The current source profiles allocate collected bilateral fees as follows. Basket canonical pools are a **Phase 2** path.

| Recipient | Phase 1 general pool | Later basket canonical pool |
| --- | ---: | ---: |
| Managed POL | 4,000 BPS | 1,500 BPS |
| Basket stakers | 0 | 3,000 BPS |
| Global STATICS stakers | 3,500 BPS | 3,000 BPS |
| Creator, fixed | 500 BPS | 500 BPS |
| Treasury | 2,000 BPS | 2,000 BPS |

The fixed creator 500 BPS sits outside the governed 9,500-BPS profile. Governance can adjust the configurable shares with `setGeneralFeeAllocation` or the later basket profile with `setBasketFeeAllocation`; a PoolId-local managed-POL override uses the current POL-plus-Treasury bucket. `setProtocolPoolFeeRate` changes a PoolId's hook rate. These changes affect future accrual, not already booked claims.

Managed POL starts inactive in a general pool. Before the creator activates it, the would-be POL share goes to Treasury. If a reward route cannot accept an asset, the configured fallback applies; do not treat an allocation percentage as a guaranteed claim.

## Swap callback and settlement

The hook records PoolManager claims in a compact swap path. It does not mint or rebalance POL positions during the swap. Any caller can use `settleProtocolPoolRevenue(poolId, asset)` for non-POL claims; a bounded maintenance tip comes only from Treasury's share. Eligible STATICS-staker ownership is fixed at fee generation, even if claim backing settles later. Activated POL inventory can be settled separately with `settleProtocolPoolPol(poolId, asset, maximumAmount)` and managed by the authorized operator.

For native ETH pools, principal, LP fees, and POL remain native ETH. ETH hook revenue uses WETH as the reward-accounting identity; the exact native receipt is wrapped at the reward boundary. One WETH reward opt-in covers WETH and native-ETH hook revenue. See [Managed POL](/docs/liquidity/permanent-liquidity) and [Global rewards](/docs/rewards/global-rewards).

Permissioned venues use a **different hook and output-fee policy** with no managed POL. See [Permissioned pools](/docs/liquidity/permissioned-pools).
